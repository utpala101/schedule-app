01 数据架构

从两个独立 store 到统一数据模型的演进过程，以及迁移中踩的坑。

数据建模

分而治之的代价

events + todos → 统一 items

一开始把「日程事件」和「待办事项」分成两个独立 store。结果用户需要在日历中给事件加象限、在待办中给任务加时间——功能越加，两边需要同步的数据越多。
根因 数据模型没有预见「一件事可以同时是日程和待办」的需求。
教训：当一个实体在 UI 不同视图中有不同呈现方式时，底层数据应统一。合并后每个 item：
// 统一 items 结构 { id, title, start, end, // 有时间 → 上日程 quadrant, dueDate, // 有象限 → 进四象限 tags, subtasks, notes, completed, created }
迁移陷阱

IndexedDB 版本升级千万别删旧 store

v1 → v2 迁移时数据丢失

升级 IndexedDB 版本号、在 onupgradeneeded 中删除旧 store 并创建新 store——然后旧数据全没了。
根因 onupgradeneeded 中无法简单读取旧 store 内容再写入新 store，getAll() 是异步的而升级事务在同步上下文中。
正确做法：保留旧 store，在应用层的 read() 方法中检测旧格式并迁移：
// 读取时检测旧格式，迁移一次，然后持久化新格式 async read() { let data = await this._readFile(); if (data.events || data.todos) { data.items = this._migrate(data); // 应用层迁移 delete data.events; delete data.todos; await this.write(data); // 持久化新格式 } return data; }

原则：数据格式向前兼容

持久化层不应假设数据格式固定不变。每次 read() 都是迁移机会。用应用层代码处理格式转换，比在 IndexedDB 升级回调中安全得多。

02 async 陷阱

JavaScript 中两个最常见的 async 相关 bug——都发生在「看起来像异步但实际不是」的地方。

致命陷阱

同步函数调 .then()，静默崩溃

应用最大的一个 bug 只需要加一个 async 关键字

在待办列表切换日期、或在日历创建事件后切到待办——数据不刷新。必须手动刷新页面。持续了整整 6 个版本未能定位。
根因 DB.getAll('items') 返回的是普通数组，不是 Promise。代码中写 .then(items => ...)——数组没有 .then()，抛出 TypeError，渲染函数从未执行。
一行修复：
// before getAll(store) { return [...(this.data[store] || [])]; } // after — async 让返回值自动变成 Promise async getAll(store) { return [...(this.data[store] || [])]; }
为什么这么难发现：因为初次加载时 Todo.init() 直接调 this.render() 正常渲染。只有视图切换时的 .then() 路径才会触发 bug。页面刷新正常 → 用户以为是自己操作不对。
设计教训

dispatchEvent 是同步的，async listener 不是

跨模块同步的微妙时序

用 document.dispatchEvent(new CustomEvent(...)) 做跨模块同步，但 listener 是 async 函数。dispatchEvent 后 listener 还没执行完，调用方已经继续往下走了。
根因 dispatchEvent 调用 listener 本身是同步的，但如果 listener 是 async，里面的 await 会让后续代码变成微任务延迟执行。
经验：跨模块同步最稳妥的方式——切换视图时直接读取最新数据，不依赖事件驱动的异步传播：
// 可靠的方式：切到待办视图时直接取最新数据 if (view === 'todo') { Todo.currentDate = new Date(); const items = await DB.getAll('items'); Todo.items = items; Todo.render(); }

原则：视图切换是天然的同步点

不要依赖异步事件传播来保持数据一致性。在视图切换这个「同步窗口」里直接读取最新持久化数据，简单可靠。

03 DOM 与布局

前端开发中 DOM 操作和布局计算相关的常见陷阱。

布局偏移

绝对定位元素忘记算兄弟元素高度

26px 的折叠条引发的偏位灾难

在周/日视图中，事件总是显示在比实际时间早一个小时的位置。点击 17:00 的格子创建事件，却出现在 16:00 的位置。点击事件编辑，保存后跑到了 15:00。
根因 折叠条（26px）是正常流布局的块级元素，占用了垂直空间。但事件的 top 值从容器顶部（0px）计算，没有把折叠条的高度 +26px。结果每个事件都偏上 26px。
// 非展开模式时，事件 top 要加上折叠条高度 _topPx(ev, th, oh, abs) { const foldH = 26; // ← 忘记这个常数导致偏位 if (abs) return (hr*60+mn)/(24*60)*(24*sh); return ((hr-oh)*60+mn)/(th*60)*(th*sh) + foldH; }
事件系统

mouseup 的 target 不是你以为的那个

拖拽释放时找不到目标元素

拖拽日历事件到目标时间槽释放，事件没有移动。每次都要拖到更下面一个槽才能生效。
根因 事件绝对定位在时间槽上方（z-index: 10）。mouseup 的目标是拖拽中的事件元素本身。e.target.closest('.cal-time-slot') 往祖先链找——事件和槽是兄弟关系，不是父子关系，永远找不到。
方案转向：mouseover → mousemove + elementsFromPoint
// 不用 closest，用元素碰撞检测 const getSlotAtPoint = (x, y) => { const els = document.elementsFromPoint(x, y); return els.find(el => el.classList.contains('cal-time-slot')); };
性能

渲染时重复注册 document 监听器

隐藏在「每次都正常执行」表象下的内存泄漏

反复拖拽和添加日程后，页面越来越卡。最终需要关闭标签页重新打开。
根因 initDragDrop() 在每次 _renderWeekDay() 中被调用。每次调用注册 4 个 document 监听器。拖拽 50 次 = 200 个事件的 listener 堆积。
// 守卫模式：仅注册一次 initDragDrop() { if (this._dragInitDone) return; this._dragInitDone = true; document.addEventListener('mousedown', onStart); document.addEventListener('mousemove', onMove); // ... }
教训：document 级别的监听器一定要只在初始化时注册一次。在渲染函数中注册相当于每次重绘都"加一层"，永远不会释放。
优化

setInterval 驱动的全量重渲染

每分钟重建整个日历 DOM

为了实现「当前时间指示线每分钟刷新」，直接调用了 this.render()——完全重建日历视图的 HTML。60s 一次，加上用户操作触发的渲染，DOM 频繁大换血。
改为仅有针对性的 DOM 更新：
// 不渲染整个视图，只移动指示线的 top const ind = document.querySelector('.cal-time-indicator'); if (!ind) { this.render(); return; } ind.style.top = newTop + 'px'; // 一次 repaint 搞定

原则：最小更新原则

每次 innerHTML = html 都会销毁重建所有 DOM 节点、丢失所有内部状态。能改一个 style.top 就不要调 render。能用 elementsFromPoint 就不要用 closest。能渲染一次就不要在渲染函数里绑监听器。

04 状态同步

模块间共享状态时的数据流管理。

状态丢失

Object.assign 把 completed 吃了

编辑表单没有完成状态字段，保存时就把原来的完成状态覆盖了

把一个待办标记为完成，然后编辑它的标题——保存后待办变成未完成。用户需要重新勾选。
根因 _readForm() 总是返回 completed: false（创建表单没有完成选项）。Object.assign(item, data) 用这个 false 覆盖了 item.completed 原有的 true。
两个方向的修复：
// 方案 A：编辑时保留旧值 const was = item.completed; Object.assign(item, data); item.completed = was; // 方案 B：编辑表单里加一个「已完成」复选框（最终方案） if (item) html += `<input type="checkbox" id="fmDone" ${item.completed?'checked':''}>`;
视图切换

刷新后永远回到日历页

单页应用需要记住用户上一次在哪个视图

用户切换到待办页、浏览数据，不小心刷新页面——回到日历。每次都要手动切回去。
// 保存当前视图到 localStorage function switchView(view) { // ... localStorage.setItem('lastView', view); } // 启动时恢复 const savedView = localStorage.getItem('lastView') || 'calendar'; switchView(savedView);

原则：单页应用的"记忆"策略

localStorage 是 SPA 最好的"记忆体"——记住用户的视图偏好、工作时段设置、主题选择。每次关键操作都同步写入。

05 UI 细节

用户体验层面容易被忽略的小问题。

交互冲突

拖拽时选中文字

mousedown 默认行为触发了文本选择

拖拽日程事件时，页面上出现选中高亮，体验极差。
onStart = (e) => { e.preventDefault(); // 一行解决 dragEl = ev; };
UX 改进

删除确认框的「原生感」问题

浏览器 confirm() 的外观和行为与页面风格割裂

confirm('删除此待办？') 弹出的对话框在页面最顶端，样式不匹配，且阻塞了 JavaScript 执行。
用 Promise + 自定义 Modal 替代：
// 返回 Promise，调用方 await showConfirm(msg) { return new Promise(resolve => { this.showModal(`...`); document.getElementById('confirmYes').onclick = () => { hide(); resolve(true); }; document.getElementById('confirmNo').onclick = () => { hide(); resolve(false); }; }); }
设计上：居中弹出、红色警告图标、匹配主题色、不阻塞页面渲染。

原则：永远不要用浏览器原生弹窗

alert()、confirm()、prompt() 在 2026 年的网页里没有任何存在的理由。它们的外观不可控、行为阻塞、用户不信任。所有弹窗都应该是页面内自定义的。
